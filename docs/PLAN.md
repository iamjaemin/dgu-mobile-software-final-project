# 식단 관리 앱 개발 계획

## 목표와 현재 범위

Kotlin + Jetpack Compose로 음식을 검색하고 섭취 중량을 기록해 끼니별·일별 영양소 합계를 확인하는 오프라인 앱을 만든다. 이번 작업은 개발 계획, 데이터 선별, 통합 JSON 생성까지다. 기존 프로젝트는 XML/AppCompat 기본 화면이며 Compose 전환은 UI 브랜치에서 진행한다.

## 브랜치 및 순서

| 브랜치 | 담당 작업 | 완료 조건 |
| --- | --- | --- |
| main | 기존 Android 프로젝트 기준점, 공통 계획·작업 규칙 | 기능별 브랜치 기준 커밋 확보 |
| feature/data-repository | 원본 프로파일링, 통합 JSON, 이후 Kotlin FoodRepository 및 로컬 저장 | 재생성 가능, 중복 코드·결측치 없음, 검색·조회 검증 |
| feature/nutrition-calculation | 영양소 모델 및 중량 비례 계산, 끼니·일별 합계 | 순수 Kotlin 테스트로 0g·소수 중량·여러 음식 검증 |
| feature/ui-compose | Compose 및 Material 3 설정, 검색·기록·일별 요약 | 검색 → 음식 선택 → g 입력 → 기록 → 합계 확인 |

계획 커밋에서 세 브랜치를 만들고 데이터 작업을 먼저 진행한다. 나머지 두 브랜치는 준비 상태로 유지한다. 공통 데이터 계약이 확정되면 해당 커밋을 반영한 뒤 각 브랜치에서 구현하고 기능 단위로 통합한다.

## 데이터 및 도메인 계약

- `data/processed/foods.json`을 유일한 배포 데이터로 관리한다. JSON 최상위는 `schemaVersion`, `foods`다. 원본 출처와 해시는 별도 매니페스트에 기록한다.
- `Food`: 식품코드, 이름, 대분류, 기원, 기준량(g), 9종 영양성분, 기준일, 원본 참조 목록. 상세 매핑은 `DATA_SOURCES.md`에 기록한다.
- `FoodRepository`: 이후 `search(query)`, `getByCode(code)` 구현. 앱 로딩 시 assets JSON을 읽고 향후 필요하면 Room으로 전환한다. JSON의 Android assets 배치는 앱 연동 단계에 진행한다.
- `MealEntry`: 고유 ID, 식품코드, 날짜, 끼니(아침/점심/저녁/간식), 섭취 g, 기록 당시 음식 이름·영양소 스냅샷. 원본 갱신이 과거 합계를 바꾸지 않도록 한다.
- `NutritionCalculator`: `성분량 × 섭취g / basisGrams`. 기준량이 100g이라고 코드에서 무조건 가정하지 않는다. 현재 선별 자료는 100g인지 별도로 검증한다.
- 열량은 원본 kcal를 사용한다. 탄단지 4/4/9 환산값으로 덮어쓰지 않는다. 계산 도중 반올림하지 않고 표시 단계에서 적용한다. 음수·NaN·무한대 중량은 거부하고 0g은 0으로 계산한다.
- 1회 제공량과 식품중량은 필수 항목이 아니므로 첫 버전은 g 입력만 지원한다. mL→g 임의 환산을 하지 않는다.

## 단계별 검증

1. 원본별 행 수, 필수 필드별 제외 수, 코드 중복 및 값 충돌을 보고서로 남기고 합계를 대사한다.
2. JSON 재생성의 바이트 일치, 숫자 단위·0 보존·결측치 제거·중복 우선순위를 테스트한다.
3. 계산 브랜치에서 기준량 100g/섭취량 150g, 0g, 소수 g 및 끼니별 합계를 테스트한다.
4. UI 브랜치에서 Compose로 전환하고 로딩·검색 결과 없음·잘못된 중량·기록 수정/삭제를 검증한다.

일일 목표는 사용자가 입력하는 방식으로 시작한다. 자동 권장 섭취량 산정, 서버·로그인·사진 인식은 초기 범위에서 제외한다.
